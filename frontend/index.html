我相信在座 90% 的同学每天都在用 Cursor / Claude Code / Copilot 写代码。但我们一起做个诚实的对比——

01

CLAUDE.md · 项目级 AI 宪法

10 分钟写一份，省 100 次重复贴上下文。4 招中性价比最高的一招。

🧠 它是什么

放在项目根目录的 Markdown 文件（Cursor 里叫 .cursor/rules/* 或 AGENTS.md， Claude Code 里叫 CLAUDE.md）。
每次 AI 启动会话都会自动读它——相当于团队的"隐形协议"。

✦ 必写的 5 个块

  • Project：项目类型、业务一句话
  • Stack：技术栈、关键库版本
  • Conventions：命名、目录、错误处理
  • Don't：明确禁止的（如 any 类型 / console.log）
  • How to run：启动 / 测试 / 部署命令

📄 Lenovo 团队 CLAUDE.md 模板（节选）

# Project
Lenovo 内部 ABC 系统 - 设备管理后台。
用户：IT 运维 ~200 人。语言：中文。

# Stack
- Frontend: Vue 3.4 + Pinia + Element Plus 2.x
- Backend:  Node.js 20 + Fastify 4 + Prisma + PG 16
- 测试: Vitest + Playwright
- 部署: Lenovo 内部 K8s（namespace=abc-prod）

# Conventions
- TS strict 模式，禁止 any
- API 路径 /api/v1/{resource}，全部蛇形
- 提交信息走 Conventional Commits
- 所有外部调用必须有 timeout + retry

# Don't
- 不要写 console.log，用 logger.info
- 不要直接拼 SQL，必走 Prisma
- 不要引新依赖前不问我

# How to run
- 启动: pnpm dev
- 测试: pnpm test
- 部署: make deploy ENV=staging
💎 团队最佳实践：把 CLAUDE.md 提交进 Git，让所有人和 AI 共享同一份"宪法"。 新人 onboarding 也比读 README 快 3 倍。
02

Cursor Rules · 全局 + 项目 双层规则

个人偏好放全局，团队约定走项目，不要混在一起。

⚙️

全局规则 个人级

位置：Cursor → Settings → Rules for AI

写什么：

  • "用中文回答"
  • "代码注释保持精简，不要废话"
  • "未确认前不要写很长的代码"
  • "提交信息用 Conventional Commits"
📁

项目规则 团队级

位置：.cursor/rules/*.mdc（多文件，可按场景拆分）

写什么：

  • frontend.mdc：Vue 风格、ESLint 约定
  • api.mdc：REST 路径、错误码规范
  • db.mdc：表设计、迁移流程
  • review.mdc：交付前自检清单
# .cursor/rules/api.mdc
---
description: REST API 设计规范
globs: "backend/**/*.ts"
alwaysApply: true
---
- 所有 API 路径前缀 /api/v1
- 响应统一格式：{ code, data, message }，code=0 表示成功
- 错误码遵循 Lenovo 内部约定，详见 @docs/error-codes.md
- 列表接口必须支持 page, pageSize，最大 pageSize=200
- 鉴权一律走 @middleware/auth.ts

💡 关键参数：globs 决定什么文件触发这条规则， alwaysApply 决定是否强制注入。用 globs 给规则"分场景"是工程化的关键。

03

MCP · 给 AI 接上"真实世界"

不再"对着空气写代码"，让 AI 真正动手做事。

MCP（Model Context Protocol）是 Anthropic 提的开放协议—— 让 AI 通过统一接口去操作浏览器、读 DB、查 Jira、调内部 API。

🌐

Browser MCP 必装

让 AI 自己开浏览器、点按钮、看截图、读 console。 前端 Bug 描述模糊？让 AI 自己看页面。

🗄️

PostgreSQL MCP 推荐

让 AI 直接连开发库查 schema / 跑 SQL。 写新接口时，schema 一秒同步给它。

📋

Jira / Confluence MCP Lenovo 适配

让 AI 读需求单、写 Confluence 文档。 "按这个 Story 写代码" 一句话搞定。

// Cursor: ~/.cursor/mcp.json （或项目级 .cursor/mcp.json）
{
  "mcpServers": {
    "browser": { "command": "npx", "args": ["-y", "@modelcontextprotocol/server-browser"] },
    "postgres": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-postgres", "$DATABASE_URL"]
    }
  }
}

🔒 团队注意：连内部数据库的 MCP 一律只给只读账号 + 测试库，绝不要连生产。

04

Hooks & Subagent · 自动化 + 分工

不用每次都打 Prompt，把流程固化成肌肉。

🪝

Hooks · 工具调用前后触发

Claude 调用工具的前 / 后 / 收尾自动跑命令——PreToolUse 拦危险、PostToolUse 自动 lint、Stop 给 checklist。

// .claude/settings.json
{
  "hooks": {
    "PostToolUse": [{
      "matcher": {
        "tool_name": "Edit",
        "file_path_regex": "backend/.*\\.js$"
      },
      "command": "node --check $CLAUDE_FILE_PATH"
    }]
  }
}
🧬

Subagent · 子智能体

把任务派给"专门角色"——每个 Subagent 有独立的 Prompt + Rules。

  • code-reviewer：只做代码审查，挑刺更狠
  • api-designer：只做接口设计
  • test-writer：只补测试用例
  • doc-writer：只写中文 README / 注释
🎯 Lenovo 团队建议：先把 CLAUDE.md + Rules 用熟（招式 1-2）， Hooks/Subagent 等团队有了协作痛点再上——不要为了用而用。

065 条 Lenovo 团队工程化经验

!

① 不要把团队的"约定"塞个人 Rules

个人偏好（语言/语气）放全局；团队规范一定提交进 Git，新人拉代码就有。

!

② CLAUDE.md 不是写一次的

项目演进时同步更新。建议在 PR 模板里加："本次是否需要更新 CLAUDE.md？"

!

③ MCP 一律给只读账号

连内部数据库 / Jira 时绝不要给写权限。AI 误操作的代价比 Bug 大得多。

!

④ AI 写的代码必须过 CR

别因为 "AI 写的"就放松审查。Reviewer 不是 AI 是你。挂你名字的代码你负责。

⑤ 最大的坑：不思考

AI 是放大器：你脑子糊涂它放大糊涂，你思路清晰它放大清晰。 "为什么这么做"永远留给自己。
Lenovo 工程师的稀缺性，不在打字速度，在判断力。
